# 全屏稳定播放时鼠标响应修复设计

## 1. 问题界定

用户确认：问题发生在**全屏稳定播放期间持续移动鼠标**，不限于进入/退出全屏动画。

区分三个指标：鼠标事件投递、应用主线程处理、屏幕光标呈现。事件处理耗时不能换算为硬件光标 FPS；录屏帧率不足时，也不能用录屏里的位置变化率替代硬件光标 FPS。

本次生产修复处理已经复现的两类应用问题：视频绘制锁等待传播到主线程；鼠标移动反复启动已显示控制栏的淡入动画。整体症状是否完全消除，仍须结合有效的呈现采样或用户实机确认，不能由本设计证明直接推出。

## 2. 多跳检索与交叉核验

### 2.1 鼠标、动画与视频同步链

1. `MainWindowController.mouseMoved` 调用预览更新、`showUI` 和隐藏计时器更新。
2. 原 `showUI` 不检查当前是否已经显示，每次都进入 `willShow`、刷新 UI 计时器、提交新的 `NSAnimationContext`。真实应用的 1000 个鼠标事件测试确认：已显示的 UI 会重新进入 `willShow`。
3. Core Animation 的 UI 提交可能请求 `ViewLayer.display`。原实现允许主线程和 `mpvGLQueue` 都获取同一个 `displayLock`。
4. 持锁的 `display` 调用 `super.display`，进而在 `draw` 内调用 `mpv_render_context_render`。
5. 本地 `deps/include/mpv/render.h` 与 [mpv 官方 render API 文档](https://github.com/mpv-player/mpv/blob/master/include/mpv/render.h) 均说明默认渲染可能等待目标呈现时间。源码中的主线程优先条件锁注释也确认存在争锁和饥饿问题。优先级只能减少饥饿，不能消除一次视频持锁造成的等待。
6. 动态测试在真实生产锁上模拟 150ms 持锁，旧代码的主线程 `display` 返回耗时约 155ms，确认上述阻塞路径可执行。

### 2.2 不能混用的外部与实验依据

- [mpv 官方 OpenGL layer](https://github.com/mpv-player/mpv/blob/master/video/out/mac/gl_layer.swift) 与本仓库结构类似，但线程策略不同，不能直接照搬。
- [Apple 的动画 API](https://developer.apple.com/documentation/appkit/nsanimationcontext/runanimationgroup(_:completionhandler:)) 与本地 AppKit SDK 用于核查动画提交方式；是否重复提交由本仓库代码及真实宿主测试直接验证。
- [Apple ScreenCaptureKit 说明](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) 及本地 `SCStream.h` 明确区分完整帧和没有新图像的 idle 回调。实际日志也出现了 120Hz 输入、约 30Hz 有效图像和大量无图像 idle 回调的组合。这不足以判断物理屏幕光标只有 30fps。
- 无绘制的高刷新提示、强制重复视频绘制、取消窗口阴影、声明窗口非不透明的对照实验没有稳定消除上述采样现象，均未纳入生产代码。
- 其他项目的阴影问题涉及不同实现，不能据此认定 IINA 存在相同根因。旧 `build` 目录的历史结果不作为本次测试通过证据。

## 3. 生产方案

### 3.1 隔离主线程与视频绘制等待

`ViewLayer.display` 在获取显示锁之前检查主线程：主线程提交 `update(force: true)` 后立即返回。实际视频绘制保留在后台，继续使用递归显示锁、显式 CATransaction、flush、skip render、OpenGL 上下文锁和生命周期读锁。删除失去用途的主线程优先条件锁。

### 3.2 合并积压请求

用短临界区保护 `updateScheduled` 和 `pendingForceDraw`。已有排队任务时，新请求只合并强制标志；任务开始时取走状态并清空排队标志。当前绘制期间的新请求可以排入一个后续任务。

### 3.3 鼠标路径只执行必要的显示转换

在 `mouseMoved` 中，仅当鼠标在窗口内，且 UI 为 `hidden` 或 `willHide` 时调用 `showUI`。`shown` 和 `willShow` 状态不重启淡入。预览、侧栏遮挡判断及隐藏计时器逻辑继续执行。其他调用方主动调用 `showUI` 的行为保持原有语义，因此更换 OSC 布局等操作仍能刷新显示。

## 4. 正确性论证

### 主线程隔离

主线程分支位于显示锁、GL 调用和事务 flush 之前。提交更新的临界区只读写布尔状态，不包含渲染、同步派发或视频等待。因此 `display` 的主线程分发路径不再等待后台视频帧释放显示锁。此结论不等于操作系统所有呈现路径均无等待。

### 队列有界

初始 `scheduled=false`。只有在锁内观察到 false 的请求能置 true 并入队。任务开始时在同一把锁下取走请求并清空 scheduled，其他请求至多安排一个后续任务。串行队列保证最多一个任务正在执行，因此活动与待执行的更新任务合计最多两个，不随事件数量增长。

### 强制请求与后续刷新不丢失

待处理强制标志按逻辑或合并，普通请求不能将 true 改回 false。任务取走状态之前的请求由当前任务覆盖；取走之后的请求由后续任务覆盖。取走操作与合并操作互斥，因此没有两个任务同时清除同一个强制标志的窗口。

### 锁顺序及重入

调度状态锁在调用 `display` 前释放；持有它时不等待显示锁。后台仍使用原递归锁处理 flush 可能引发的重入。GL 锁与生命周期锁的先后顺序不变，已停止视图仍在原有生命周期检查处退出。

### UI 状态转换

`hidden` 收到鼠标移动后进入显示流程；`willHide` 收到鼠标移动后反转隐藏；`willShow` 与 `shown` 收到移动时保持显示过程。其余鼠标处理仍执行，故避免重复淡入不会阻止预览更新、自动隐藏计时或已隐藏控制栏的重新显示。

### 视频同步

没有修改 mpv 的目标时间等待、视频速度、屏幕显示模式、CVDisplayLink 回调和空闲策略。强制绘制仍通过原有绘制实现完成，不使用禁用同步来降低等待。

## 5. 验证架构与边界

- 机制层：编译完整生产 `ViewLayer.swift` 和生产锁；播放器依赖替身用于确定性地控制锁、队列与生命周期，不模拟调度算法。
- 应用层：新增独立测试 Scheme，以真实 IINA、libmpv、AppKit、OpenGL 执行播放、全屏、鼠标、暂停及截图测试。测试副本使用独立 bundle identifier，测试播放器采用生产播放器池的创建/关闭方式。
- 输入层：独立工具投递系统鼠标事件，并记录真实投递频率；应用本地事件监视器记录实际到达主线程的事件和延迟。该测试不创建录屏流。
- 呈现诊断：只捕获生成视频内 280×50 点区域，检查输入频率、有效图像频率、覆盖时长、箭头识别和视频背景。采样能力不足时结果为“未验收”，不得当成产品通过或硬件 FPS 下降的证明。
- 测试偏好通过临时参数域覆盖并恢复；安装版应用及其偏好不用于测试宿主。按用户本次明确要求添加测试，覆盖 CONTRIBUTING 中不添加测试的通用建议。
- 验证范围为本机 SDR 生成素材及内置屏幕；HDR、多屏、其他系统版本和物理屏幕光学测量不在已证明范围内。
