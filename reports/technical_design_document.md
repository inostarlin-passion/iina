# 原生全屏鼠标降帧修复设计

## 1. 问题与约束

用户确认：降帧发生在全屏稳定播放期间持续移动鼠标；必须保留原生全屏及独立桌面，不采用传统全屏回退。

基线为 `bcf566a45740efb7a9fd580a03cc8070c6f07d1a`。该版本已经包含主线程绘制请求异步转交、更新合并和控制栏淡入幂等处理，但上一轮原生全屏呈现采样仍有未验收项。本轮不把事件处理延迟当作光标呈现帧率，继续追踪真实绘制边界。

## 2. 检索链与交叉核验

### 2.1 绘制目标被改变

1. `ViewLayer.draw` 取得 Core Animation 提供的 CGL 上下文及当前写 FBO，将该目标传给 `mpv_render_context_render`。
2. 本地 `deps/include/mpv/render_gl.h` 的 OpenGL state 章节及 [mpv 官方文档](https://github.com/mpv-player/mpv/blob/master/include/mpv/render_gl.h) 说明：mpv 会尝试把上下文归回 OpenGL 标准默认状态；其契约不是保留调用方的所有绑定。
3. 运行时追踪确认：进入回调时读、写 FBO 为非零目标，例如 `(18,18)`、`(8,8)`；mpv 返回后均为 `(0,0)`。现有代码随后只执行 `glFlush`，没有恢复调用方的目标。
4. [CAOpenGLLayer 接口](https://developer.apple.com/documentation/quartzcore/caopengllayer) 及本地 SDK 声明说明绘制上下文与图层的渲染目的地关联。mpv 的默认状态与该回调入口状态不同，应由嵌入方明确恢复边界状态。
5. 新回归测试使用真实 GL 对象、完整生产 `draw` 和只模拟 mpv 默认状态清理的 C 边界替身。修复前两个断言失败：写目标 `0 != 1`，读目标 `0 != 2`。此结果与实际 mpv 追踪一致。

### 2.2 对照排除与冲突消解

- 普通 AppKit 30Hz 纯色窗口、默认 OpenGL 主线程绘制、默认 OpenGL 后台绘制、生产上下文/像素格式的后台纯色绘制，均能在原生全屏获得高频光标采样。因此不能把问题简单归结为“所有原生全屏都无法采样”或“后台 OpenGL 必然限速”。
- 真实视口为约 `3456×2168`、图层约 `1728×1084`、缩放为 2，没有观察到额外一次 Retina 放大。
- 在绘制回调中受控停留 150ms 时，主线程获取 Core Animation 全局锁约 0.01ms，反驳了回调必然一直持有该全局锁的假设。
- 官方支持的 `video-timing-offset=0` 对照、扩大捕获区域、减少自有队列的强制事务刷新，均没有提供稳定改善证据，已撤销这些实验，不改生产时序或刷新策略。
- 上游 [#5709](https://github.com/iina/iina/issues/5709) 与 [#5159](https://github.com/iina/iina/issues/5159) 涉及切换应用、RTSP 等不同条件，不能代替本任务的证据。
- 同顺序配对测试中，基线的 30fps 原生全屏光标位置变化采样为约 **89.13Hz**，当时有效图像约 **112.61Hz**、实际输入约 **120.38Hz**，采样能力足够，仍未达到既定 96Hz 阈值。修复后相同场景约 **110.36Hz**。

据此确认帧缓冲状态泄漏是实际缺陷；修复后多轮有效软件采样通过，支持它与目标症状相关。对 Core Animation 私有内部缓存的具体实现不作断言。

## 3. 生产设计

唯一新增生产修改位于 `iina/ViewLayer.swift` 的 `draw`：

1. 保存入口写 FBO `D` 和入口读 FBO `R`，分别保存，不假设相等。
2. 保留原有清屏、mpv 渲染、截图与视频时序处理。
3. 在当前生命周期读锁范围内使用 `defer`，返回 Core Animation 前分别恢复写、读绑定。

既有主线程异步分发、队列合并、递归显示锁、显式事务与 flush、CVDisplayLink、全屏状态机均保留。没有新增显示模式回退、额外重绘循环或全局偏好变更。

## 4. 正确性证明

### 4.1 帧缓冲后置条件

设回调入口绑定为 `(D,R)`。进入已初始化的绘制分支后，两个值在调用 mpv 前保存。mpv 可把它们改成 `(0,0)` 或其他值；无论其返回值如何，离开作用域前均执行 `bindDraw(D)`、`bindRead(R)`。故回调边界后置条件为：

`(drawFramebuffer, readFramebuffer) = (D,R)`。

使用不同读、写 FBO 的回归用例可发现误把两个目标恢复成同一个值的问题。

### 4.2 生命周期与资源安全

停止视图在任何新增 GL 操作前退出。保存与恢复均位于原有生命周期读锁内，恢复先于该读锁释放；GL 上下文仍由原调用链提供并保护。恢复操作不创建或销毁 FBO，不延长其所有权。截图先通过原逻辑读取视频目标，再由外层清理恢复入口绑定。

### 4.3 时序及输出语义

mpv 的目标 FBO、尺寸、翻转和深度参数保持原值；目标时间等待、视频同步参数与显示链接回调保持原值。新增操作只恢复上下文状态，不增加视频帧、不提前呈现帧，也不改变全屏控制器与独立桌面路径。

### 4.4 并发与队列

新增代码在现有绘制回调内执行，没有增加锁或同步派发，没有改变锁顺序。已有每实例至多一个活动更新和一个排队更新的合并机制继续生效；原有强制重绘、空闲与恢复语义由回归测试覆盖。

### 4.5 证明范围

以上证明针对帧缓冲状态、生命周期、时序配置和控制路径。光标帧率是系统合成结果，需要动态证据；不能从状态不变量直接推导所有机器上每一帧的物理呈现时间。

## 5. 验证设计

- 机制测试：完整生产 ViewLayer 与真实 OpenGL；D6 仅在进程边界替换 mpv 的状态清理，不把替身链接进真实应用。
- 应用测试：真实 IINA/libmpv，原生/传统全屏、暂停空闲、恢复、截图、窗口尺寸恢复、鼠标处理。
- 呈现测试：24/30/60fps × 窗口/原生/传统全屏，共九阶段；实际投递与捕获频率、覆盖时长及箭头识别均达标后才评价位置变化率。
- 无录屏输入测试：真实系统事件投递与 NSEvent 到达延迟，独立于呈现采样。
- 四组图形对照帮助区分窗口系统、OpenGL、队列和生产上下文因素。
- 测试驱动器在构建失败时清除旧执行日志，避免把上一轮结果误用为本轮证据。

软件采样不等于高帧率相机对物理面板的测量。已验证范围为本机内置 120Hz 屏幕与生成的 SDR 素材；HDR、多屏及其他设备的光学表现没有被冒充为已测结果。
